# ТЗ v1: Умный парсинг автозапчастей и применяемости

> **Проект:** MAP — платформа подготовки и публикации автозапчастей
> **Версия:** 1.3
> **Статус:** enrichment MVP, platform knowledge graph, `catalog_domain`, классификация товара, массовая классификация и tenant-категории MVP реализованы; текущий P0 по категориям закрыт; следующий P0 — source quality policy, приоритеты нескольких источников и conflict resolution
> **Главное архитектурное решение:** модуль обогащает существующий `Product`, а не создает параллельную модель товара
> **Multi-tenant решение:** фича является общей возможностью платформы; tenant-товары обогащаются в своем контексте, а справочные знания о применяемости могут храниться на уровне платформы

---

## 1. Цель

Реализовать модуль обогащения собственной базы товаров. По паре `brand + article` система получает из внешних каталогов только справочно-технические данные, структурирует их, сохраняет в текущую товарную модель проекта и делает результат доступным в Django Admin и API.

Модуль не является источником складских или коммерческих данных. Он не должен обновлять остатки, наличие на складе, закупочные цены, отпускные цены или любые поля, которые отражают реальные условия продажи нашей компании.

Модуль является платформенной фичей MAP, а не кастомной разработкой под одного клиента. В SaaS может быть много tenant-ов, и каждый tenant имеет свой каталог товаров. Поэтому парсер, реестр источников и правила разбора общие для проекта, но результат всегда применяется в контексте конкретного tenant.

Пример входа:

```text
brand: BREMBO
article: P50136
source: tachka
```

Ожидаемый результат:

```text
товар
характеристики
OEM и cross-коды
применяемость к авто
изображения или URL изображений
полезные факты для описания
черновик достоверного описания
источник данных
лог парсинга
статус качества данных
```

## 3. Multi-tenant модель фичи

### 3.0 Нишевая применимость фичи

Автозапчастный enrichment не должен быть обязательной логикой для всех tenant-ов.
Если tenant продает украшения, одежду или другой неавтомобильный товар, платформа
должна работать без конфликтов:

```text
импорт товаров -> Product
AI-описание по обычным данным -> разрешено
поиск изображений -> разрешено
автозапчастный parser/fitment/OEM enrichment -> не запускать автоматически
```

Реализован явный tenant/catalog capability:

```text
catalog_domain = auto_parts | mixed | generic | jewellery | apparel | other
```

Правило запуска:

```text
catalog_domain = auto_parts -> parser/OEM/fitment enrichment разрешен
catalog_domain = mixed -> parser/OEM/fitment enrichment разрешен только для товаров-кандидатов автозапчастей
catalog_domain not in auto_parts/mixed -> parser/OEM/fitment enrichment запрещен
catalog_domain not in auto_parts/mixed -> обычная AI-генерация и поиск фото разрешены
```

Это защищает tenant-ов неавтомобильных ниш от конфликта предметных правил.
Например, tenant с украшениями не должен получать попытки искать OEM, применяемость
или автомобильные категории, но должен продолжать пользоваться базовой генерацией
описания по своим данным. Если tenant смешанный, массовое действие должно
обогащать только товары, похожие на автозапчасти, и пропускать остальные.

Для смешанных каталогов используется tenant-scoped классификация товара:

```text
ProductCatalogClassification
domain = auto_parts | generic | jewellery | apparel | unknown
confidence
source = rules | manual | ai
reason
needs_review
```

Классификация не заменяет `Product.category_1c`. Она нужна как guardrail перед
domain-specific действиями: auto-parts parser можно запускать только для товаров
с `domain=auto_parts` и достаточной уверенностью.

Для уже импортированных каталогов нужен отдельный bulk action:

```text
classify_catalog_domain
```

Он не делает внешних запросов, работает batch-ами, заполняет
`ProductCatalogClassification` и позволяет оператору до enrichment видеть, какие
товары являются автозапчастями, украшениями, одеждой или требуют проверки.

### 3.0.1 Домены vs категории товаров

Нужно жестко разделять два разных понятия:

```text
CatalogDomain / ProductCatalogClassification.domain
TenantCatalogCategory / Product.category_1c / будущая category_id
```

`CatalogDomain` и `ProductCatalogClassification.domain` — это platform guardrail.
Он отвечает на вопрос:

```text
какие domain-specific возможности можно запускать для tenant-а или товара?
```

Например:

```text
auto_parts -> можно запускать parser/OEM/fitment
jewellery -> нельзя запускать auto-parts parser
unknown -> нужна проверка или обычный AI без parser
```

Этот слой должен управляться платформой и суперюзером, потому что ошибка в нем
может привести к запуску неправильного parser-а, неверной применяемости или
загрязнению справочного графа.

Реализация platform domain:

```text
CatalogDomain
slug
name
short_name
description
seo_title
seo_description
seo_keywords
seo_h1
canonical_path
og_title
og_description
og_image_url
meta_robots
is_active
is_system
sort_order
supports_auto_parts_enrichment
requires_product_classification
```

Суперюзер управляет `CatalogDomain` в Django admin. Dashboard tenant-а получает
активные домены через API и не содержит hardcoded бизнес-названия доменов.

Категории товаров — это бизнес-структура каталога tenant-а:

```text
Тормозные колодки
Амортизаторы
Кольца
Браслеты
Платья
```

Их должен редактировать tenant в dashboard. Категория может быть привязана к
platform domain, но не должна сама становиться domain guardrail.

Реализованная MVP-модель:

```text
TenantCatalogCategory
tenant
name
parent
domain
aliases
external_source
external_id
default_image_s3_key
is_active

TenantCategoryMapping
tenant
source_category
category
```

Практическое правило:

```text
tenant редактирует категории
суперюзер/платформа контролирует домены и parser capabilities
classification использует категорию как сигнал, но не доверяет ей без confidence
```

Это нужно, чтобы tenant мог удобно управлять каталогом, но не мог случайно
включить auto-parts enrichment для украшений или другого неавтомобильного товара.

### 3.1 Уровень платформы

На уровне всего проекта общими являются:

```text
код парсеров
реестр источников
правила нормализации
правила confidence/need_review
очереди Celery
общая observability по источникам
```

Эти компоненты не принадлежат отдельному tenant-у.

### 3.2 Уровень tenant-а

На уровне tenant-а хранятся:

```text
Product
ProductAttribute
ProductCrossCode
VehicleFitment
ProductImage
ProductParseJob
ProductEnrichmentFact
```

Каждая запись результата должна быть привязана к `tenant` напрямую или через `Product.tenant`.

### 3.3 Главное правило записи

Парсер никогда не должен записывать обогащение “в общий каталог” без tenant.

Правильно:

```text
tenant + brand + article -> найти Product этого tenant -> записать enrichment этому tenant
```

Неправильно:

```text
brand + article -> найти любой Product -> записать enrichment без tenant
```

### 3.4 Возможный общий cache

Допускается общий platform-level cache сырого результата парсинга по ключу:

```text
source_id + normalized_brand + normalized_article
```

Но такой cache не должен считаться пользовательскими данными tenant-а. При применении результата к товару данные копируются/сохраняются в tenant-scoped модели.

### 3.5 Platform-level knowledge base артикулов и применяемости

Для быстрой повторной выдачи OEM/Cross-связей и применяемости между tenant-ами нужен отдельный слой справочных знаний проекта.

Смысл:

```text
если один tenant уже обогатил BREMBO P50136,
другой tenant с тем же брендом/артикулом или OEM-кодом должен получить известные OEM/Cross-связи и марки/модели мгновенно,
без обязательного повторного парсинга внешнего источника
```

Этот слой не является каталогом товаров tenant-а и не содержит коммерческие данные tenant-а. Он хранит только технические справочные связи:

```text
нормализованный бренд
нормализованный артикул
нормализованный OEM/Cross-код
тип связи: OEM / Cross / Analogue / Replacement / Trade / Unknown
марка авто
модель авто
поколение/кузов
модификация
годы выпуска
двигатель/код кузова
источник
confidence
needs_review
```

Tenant-scoped `VehicleFitment` остается нужным:

```text
Product конкретного tenant-а -> примененная применяемость для UI/API/AI
```

Platform-level справочник нужен для накопления и переиспользования знаний:

```text
GlobalPart -> глобальный нормализованный артикул без tenant-коммерции
GlobalPartRelation -> связь артикулов: OEM, cross, analog, replacement, trade
GlobalPartFitment / PartVehicleIndex -> быстрый поиск применяемости по article/OEM
VehicleMake / VehicleModel / VehicleGeneration / VehicleModification -> нормализованный справочник авто
```

Важное ограничение:

```text
GlobalPartRelation помогает находить аналоги и связанные OEM/Cross-коды,
но сама по себе не доказывает применяемость к автомобилю.
Конкретные марки/модели должны приходить из VehicleFitment или GlobalPartFitment.
```

Главное правило:

```text
platform knowledge можно читать для любого tenant-а,
но запись результата в Product/VehicleFitment всегда делается tenant-aware
```

Практический порядок enrichment job:

```text
1. Найти GlobalPart по brand + article.
2. Если есть trusted GlobalPartRelation — применить к ProductCrossCode tenant-а.
3. Если есть trusted GlobalPartFitment — применить к VehicleFitment tenant-а.
4. Если данных достаточно — завершить job без внешнего fetch.
5. Если данных нет или они reviewable — идти во внешний источник.
```

Это снижает нагрузку на источники, уменьшает риск блокировок и ускоряет повторное
обогащение одинаковых товаров у разных tenant-ов.

### 3.6 Source quality policy

Platform knowledge graph должен расти осторожно. При добавлении новых источников
нельзя просто складывать все данные в одну кучу, потому что источники будут
отличаться качеством, полнотой и форматом.

Для каждого источника нужны правила:

```text
source_id
label
priority
trust_score
batch_size
min_pause_seconds
default_pause_seconds
capabilities
transport
```

Минимальные capabilities:

```text
supports_product_page
supports_search
supports_fitments
supports_images
supports_related_parts
```

Минимальные transports:

```text
httpx
browser
api
```

`httpx` остается транспортом по умолчанию. Browser/stealth transport, например
`CloakBrowser`, можно рассматривать только для конкретных источников, где обычный
HTML/API fetch не работает из-за JS/anti-bot. Он не должен становиться обязательной
зависимостью core parser.

Confidence rules:

```text
trusted source + structured parser match -> confidence 0.9-1.0
search result / analogue block -> confidence 0.7-0.9
unknown relation type -> confidence <= 0.8 + needs_review
missing make/model in fitment -> needs_review
source conflict -> needs_review
```

Автоматически применять к tenant-товару можно только trusted данные:

```text
needs_review = false
confidence >= auto_apply_min_confidence
relation_type != Unknown
```

Conflict rules:

```text
не удалять старые полезные данные при конфликте
не перетирать confirmed данные менее надежным источником
сохранять provenance каждой связи
помечать конфликтующие записи needs_review
не считать аналог доказанной применяемостью
```

Provenance обязателен для всех platform-level записей:

```text
source_id
source_url
raw_text
confidence
needs_review
last_seen_at
```

### 3.7 Категории автозапчастей

Категоризация запчастей полезна и нужна, но ее нельзя превращать в полный TecDoc
на раннем этапе. Нужен легкий platform-level taxonomy слой:

```text
PartCategory
normalized_name
parent
aliases
fitment_required
```

Базовая модель `PartCategory` реализована как platform-level read-only справочник
для админки и будущего наполнения. Она пока не перетирает `Product.category_1c` и
не является обязательной связью товара.

Зачем это нужно:

```text
понимать, где применяемость обязательна, а где нет
улучшать AI-описания без выдумок
фильтровать каталог tenant-а
сопоставлять категории разных источников
не запускать auto-fitment для неавтомобильных товаров
```

Важно: `Product.category_1c` остается tenant/source полем. Platform category не
должна перетирать категорию из 1С; она может быть отдельным enrichment-фактом или
будущей связью, применяемой только при достаточном confidence.

### 3.8 Конфликты категоризации и доменизации

При внедрении tenant-категорий и domain-классификации есть несколько опасных
мест. Их нужно закрывать правилами, а не ad-hoc проверками во view.

#### Конфликт 1: tenant-категория ошибочно привязана к domain

Пример:

```text
Tenant category "Кольца" -> domain=auto_parts
```

Правило:

```text
category domain является сигналом, но ProductCatalogClassification должна сохранять confidence/reason
низкая уверенность -> needs_review
auto-parts parser не запускается при unknown/needs_review
```

#### Конфликт 2: один tenant продает несколько ниш

Пример:

```text
tenant catalog_domain=mixed
каталог содержит "Колодки тормозные" и "Золотое кольцо"
```

Правило:

```text
tenant capability разрешает mixed
каждый Product проходит ProductCatalogClassification
bulk enrichment пропускает не-auto_parts товары
обычная AI-генерация остается доступной всем товарам
```

#### Конфликт 3: Product.category_1c пришла из 1С и отличается от tenant-категории

Правило:

```text
Product.category_1c не перетирается enrichment-ом
TenantCatalogCategory хранится отдельно
маппинг source category -> tenant category должен быть явным
```

#### Конфликт 4: platform PartCategory и tenant category имеют одинаковые названия

Пример:

```text
PartCategory "Амортизаторы"
TenantCatalogCategory "Амортизаторы"
```

Правило:

```text
PartCategory = platform taxonomy автозапчастей для enrichment/fitment rules
TenantCatalogCategory = пользовательская структура каталога tenant-а
между ними может быть связь, но нельзя использовать одну таблицу для обеих задач
```

#### Конфликт 5: новый domain требует новый parser

Пример:

```text
domain=jewellery
```

Правило:

```text
нельзя переиспользовать auto-parts parser
нужен отдельный domain-specific enrichment pipeline
до появления pipeline разрешены только generic AI/image flows
```

#### Конфликт 6: ручное исправление классификации

Правило:

```text
manual classification имеет source=manual
rules-based bulk classification не должен молча перетирать manual без отдельного флага force
история изменения или хотя бы updated_at/source/reason обязательны
```

Реализовано:

```text
ProductEnrichmentService.classify_product_catalog_domain(..., force=False)
сохраняет существующую source=manual классификацию без изменений.

force=True разрешает осознанно пересчитать manual и заменить её rules-результатом.
Фоновые bulk rules не должны передавать force=True.
```

## 4. Что НЕ делаем в MVP

Чтобы не раздуть фичу и не продублировать существующую архитектуру, в MVP не делаем:

- Отдельную модель `AutoPart`, если данные относятся к товару `Product`.
- Отдельную модель `PartImage`, потому что уже есть `ProductImage`.
- Полноценный справочник брендов `PartBrand`, пока нет доказанной проблемы с алиасами.
- Массовый импорт тысяч артикулов.
- Парсинг и обновление цен.
- Парсинг и обновление остатков.
- Парсинг и обновление наличия на складе.
- Историю остатков.
- Автоматическое AI-достраивание применяемости.
- TecDoc-подобную базу совместимости.
- Полный TecDoc-классификатор категорий.
- Полную поддержку нескольких источников без source quality policy.
- Полный platform-level справочник `VehicleGeneration/VehicleModification`.
- Сложную антибан-систему, кроме базовых timeout/rate limit/retry.
- Browser/anti-bot runtime как обязательную зависимость core parser.
- Принудительную автозапчастную логику для tenant-ов с `catalog_domain != auto_parts`.

## 5. Термины

**Product** — текущий товар проекта, который может быть импортирован из 1С/CSV или создан вручную. Парсер обогащает этот товар справочными данными.

**Tenant-scoped enrichment** — результат обогащения, записанный в каталог конкретного tenant-а.

**Platform parser** — общий код парсера и правил разбора, переиспользуемый всеми tenant-ами.

**Парсинг** — загрузка страницы источника и извлечение фактов без генерации выдуманных данных.

**Обогащение товара** — добавление к `Product` характеристик, применяемости, OEM/cross-кодов, изображений и фактов для описания.

**Коммерческие данные** — цена, остаток, наличие, склад, условия поставки. Для этой фичи они считаются вне scope.

**Источник парсинга** — внешний сайт/каталог, например `tachka.ru`.

**Parse job** — запись о попытке парсинга: вход, источник, статус, raw HTML, parsed JSON, ошибка.

**need_review** — статус, при котором данные технически получены, но требуют ручной проверки.

## 6. Основной пользовательский сценарий

Админ или пользователь запускает парсинг:

```json
{
  "brand": "BREMBO",
  "article": "P50136",
  "source": "tachka"
}
```

Система:

1. Проверяет наличие `tenant`.
2. Проверяет, что товар принадлежит этому tenant, если передан `product_id`.
3. Валидирует `brand` и `article`.
4. Нормализует артикул.
5. Создает `ProductParseJob` со статусом `pending` и привязкой к tenant.
6. Ставит Celery-задачу.
7. Celery-задача переводит job в `running`.
8. Строит URL источника.
9. Загружает HTML с timeout и ограничением размера.
10. Парсит данные.
11. Валидирует обязательные поля.
12. Находит существующий `Product` внутри этого tenant или создает новый только при явно разрешенном сценарии.
13. Сохраняет характеристики.
14. Сохраняет OEM/cross-коды.
15. Сохраняет применяемость.
16. Извлекает полезные факты для достоверного описания.
17. Передает URL изображений в существующий image pipeline или сохраняет как кандидаты, в зависимости от этапа.
18. Сохраняет raw HTML и parsed JSON в job.
19. Выставляет статус `success`, `need_review`, `not_found` или `failed`.
20. Возвращает результат в админке/API.

## 7. Источники данных

### 7.1 MVP-источник

```text
tachka.ru
```

Scope источника:

```text
весь доступный каталог tachka.ru, который можно адресовать или найти по brand + article
```

Парсер не должен быть завязан на один конкретный товар. `BREMBO P50136` используется только как пример входных данных и один из тестовых fixtures.

Базовый шаблон URL, если страница товара доступна напрямую:

```text
https://tachka.ru/{brand}/{article}
```

Пример тестового URL:

```text
https://tachka.ru/brembo/P50136
```

Если у источника фактическая навигация устроена иначе, parser source должен инкапсулировать это внутри себя:

```text
brand + article -> search/catalog page -> product page -> parsed enrichment data
```

Важное правило для аналогов:

```text
аналоги могут отсутствовать на странице конкретного товара,
но быть доступны в поисковой выдаче, OEM-выдаче, API поставщика или TecDoc-подобном каталоге.
```

Поэтому source parser должен поддерживать два независимых сценария:

```text
parse product page -> характеристики, изображения, применяемость, OEM/Cross
parse search/results page -> связанные артикулы: OEM, cross, analogue, replacement
```

Связанные артикулы сохраняются как platform-level `GlobalPartRelation`.
Они не должны автоматически считаться доказанной применяемостью к автомобилю.
`VehicleFitment` создается только если источник явно дал применяемость.

### 7.2 Источники будущих этапов

```text
exist.ru
emex.ru
autodoc.ru
каталоги с API
TecDoc-подобные каталоги
```

### 7.3 Архитектурное требование

Парсер должен быть pluggable:

```text
BasePartParser
TachkaPartParser
future: ExistPartParser
future: EmexPartParser
future: CatalogApiParser
```

При этом в MVP достаточно реализовать только `TachkaPartParser`.

Явно не извлекаем и не сохраняем как результат этой фичи:

```text

```

### 8.2 Куда сохраняем

| Данные | Куда сохранять |
|---|---|
| Название | `Product.name`, только если товар создан парсером или поле пустое |
| Бренд | `Product.brand`, только если товар создан парсером или поле пустое |
| Артикул | `Product.article`, только если товар создан парсером |
| Категория | `Product.category_1c`, если поле пустое или источник помечен как trusted |
| Характеристики | `ProductAttribute` |
| OEM/cross | `ProductCrossCode` + compatibility sync в `Product.oem_numbers/cross_numbers` |
| Применяемость | `VehicleFitment` + compatibility sync в `Product.applicability` |
| Изображения | `ProductImage` через существующий pipeline |
| Факты для описания | `ProductEnrichmentFact` или `ProductAttribute` на MVP |
| Дата обогащения | `ProductParseJob.finished_at`; `Product.sync_at` не использовать для этого |
| Источник | через `ProductParseJob.source_id`, не через `DataSourceConnection` в MVP |

### 8.3 Что запрещено менять

Модуль обогащения не должен изменять:

```text
Product.price
Product.stock_qty
Product.warehouse
Product.export_enabled
данные листингов
данные marketplace accounts
```

Если внешняя страница содержит цену или наличие, эти данные можно сохранить только в `raw_html/raw_text/parsed_data` для отладки, но нельзя применять к товару.

### 8.4 Важное решение по `DataSourceConnection`

`DataSourceConnection` сейчас описывает tenant-источники импорта: 1С, XML, CSV. Каталог `tachka.ru` не является пользовательским подключением тенанта, поэтому на MVP не нужно смешивать его с `DataSourceConnection`.

Если позже появятся каталоги или поставщики с личными API-ключами, их можно будет добавить в `DataSourceConnection` как новый тип только после отдельного проектирования. Для enrichment MVP это не требуется.

## 11. Применяемость к авто

### 11.1 Пример строки

```text
E-CLASS (W213) 01.2016-2023 E 220 d 4-matic (213.005) 194 л.с
```

### 11.2 Целевая структура

```json
{
  "make": "MERCEDES-BENZ",
  "model": "E-CLASS",
  "generation": "W213",
  "date_from": "01.2016",
  "date_to": "2023",
  "modification": "E 220 d 4-matic",
  "engine_code": "213.005",
  "power_hp": 194,
  "raw_text": "E-CLASS (W213) 01.2016-2023 E 220 d 4-matic (213.005) 194 л.с"
}
```

### 11.3 Новая модель

```text
VehicleFitment
```

Поля:

```text
product
make
model
generation
date_from
date_to
modification
engine_code
power_hp
raw_text
source_id
confidence
needs_review
created_at
updated_at
```

### 11.4 Связь с текущим `Product.applicability`

`Product.applicability` оставить для обратной совместимости и быстрых сценариев.

После парсинга:

- структурные данные сохраняются в `VehicleFitment`;
- краткая JSON-копия может сохраняться в `Product.applicability`;
- API должен отдавать структурные данные из `VehicleFitment`.

### 11.5 Правила качества

Если строка применяемости не парсится уверенно:

```text
needs_review = true
confidence < 0.7
```

Если у товара нет применяемости:

```text
ProductParseJob.status = need_review
```

Исключение: если категория товара по природе может не иметь применяемости, это правило уточняется позже.

### 11.6 Быстрое сопоставление по справочнику

После появления platform-level knowledge base система должна работать в таком порядке:

1. Нормализовать `brand + article` товара tenant-а.
2. Нормализовать все известные OEM/Cross-коды товара.
3. Найти уже известные связи артикулов в `GlobalPartRelation` по:

```text
normalized_brand + normalized_article
normalized_oem_code
normalized_cross_code
```

4. Скопировать найденные достоверные связи в tenant-scoped `ProductCrossCode`.
5. Найти уже известную применяемость в глобальном индексе по:

```text
normalized_brand + normalized_article
normalized_oem_code
normalized_cross_code
```

6. Если применяемость найдена с достаточным `confidence`, применить ее к товару tenant-а через `VehicleFitment`.
7. Если данных нет или уверенность низкая, поставить enrichment job во внешний источник.
8. После успешного парсинга обновить tenant-scoped enrichment и platform-level knowledge base.

Это дает два режима:

```text
cache hit -> применяемость появляется моментально
cache miss -> запускается обычный parser enrichment
```

### 11.7 Нормализованный справочник автомобилей

Для устойчивого поиска и фильтров нужны справочные сущности:

```text
VehicleMake
VehicleModel
VehicleGeneration
VehicleModification
VehicleAlias
GlobalPartFitment
```

Текущий статус на 01.06.2026:

- `VehicleMake` и `VehicleModel` реализованы.
- `VehicleGeneration` реализован и связан с `GlobalPartFitment`.
- Алиасы марок/моделей реализованы через массив `aliases`.
- `GlobalPartFitment` хранит raw `make/model/generation/modification` и nullable
  ссылки `vehicle_make` / `vehicle_model` / `vehicle_generation`.
- Raw строки применяемости нельзя удалять: они остаются источником правды для
  отладки и повторной нормализации.
- Следующий P0 — усилить накопление применяемости: по товару tenant-а искать
  `GlobalPart`, применять trusted `GlobalPartFitment`, запускать внешний источник
  при нехватке данных и передавать агенту только проверенные авто-факты.
- Поиск товаров tenant-а по авто — следующий продуктовый слой, но не текущий
  приоритет.

Минимальные поля `VehicleMake`:

```text
name
normalized_name
aliases
```

Минимальные поля `VehicleModel`:

```text
make
name
normalized_name
aliases
```

Минимальные поля `VehicleGeneration`:

```text
model
name
body_code
date_from
date_to
```

Минимальные поля `GlobalPartFitment`:

```text
normalized_brand
normalized_article
normalized_oem_code
make
model
generation
modification
engine_code
power_hp
source_id
source_url
confidence
needs_review
last_seen_at
```

Vehicle KB v2 должен расширить `GlobalPartFitment` ссылкой на
`VehicleModification`, но только nullable. Если нормализация не уверена, raw
`generation/modification/engine_code` сохраняются без FK и могут попасть в
review.

Главный пользовательский сценарий на этом этапе:

```text
Product из 1С: name + brand + article
  -> найти/создать GlobalPart
  -> применить уже известные trusted fitments/OEM/cross
  -> если данных мало, запустить внешний enrichment source
  -> сохранить новые fitments/OEM/cross/аналоги в global graph
  -> обновить tenant VehicleFitment
  -> отдать AI-агенту конкретные марки/модели/поколения для описания
```

AI не должен писать "подходит для ..." по догадке из названия. Такая фраза
разрешена только если есть trusted `VehicleFitment` или trusted
`GlobalPartFitment`, примененный к товару tenant-а.

### 13.2 Статусы


### 13.3 Правила статусов

`pending` — job создан, задача еще не стартовала.

`running` — Celery-задача начала выполнение.

`success` — товар найден, обязательные данные сохранены, критичных замечаний нет.

`need_review` — данные сохранены, но есть сомнения: нет применяемости, мало обязательных полей, низкая уверенность разбора.

`not_found` — источник вернул 404 или понятный признак отсутствия товара.

`failed` — техническая ошибка, изменение верстки, timeout после retry, ошибка валидации обязательных данных.

## 19. Полезное описание товара

### 19.1 Цель

Модуль должен помогать делать карточку товара полезнее для покупателя: объяснять, что это за деталь, для чего она нужна, какие у нее важные технические параметры и к каким автомобилям она подходит.

Описание не должно быть рекламной фантазией. Оно должно строиться только на сохраненных фактах:

```text
название
бренд
артикул
категория
характеристики
OEM/cross-коды
применяемость
исходный текст источника
```

### 19.2 Что сохранять

Рекомендуется добавить отдельную сущность на этапе MVP или 2:

```text
ProductEnrichmentFact
```

Поля:

```text

fact_type
name
value
raw_text

needs_review
created_at
updated_at
```

`fact_type`:

```text

```

### 19.3 Как генерировать описание

Существующая кнопка в дашборде:

```text
Сгенерировать описание
```

сейчас запускает AI-агента, который пишет `title_ai` и `description_ai` из сырых данных `Product`. После внедрения enrichment-модуля эта кнопка должна использовать более качественный pipeline:

```text
Product -> enrichment parser -> structured facts -> AI description agent -> title_ai/description_ai
```

MVP:

```text
если enrichment уже свежий и успешный:
  сразу запускать AI-агента с enrichment context

если enrichment отсутствует или устарел:
  сначала поставить parse/enrichment job
  после success/need_review запустить AI-агента
  если enrichment failed/not_found, дать агенту работать по старым данным, но пометить confidence ниже
```

Этап 2:

```text
сделать orchestration-задачу generate_enriched_description
показывать в UI этапы: обогащение -> генерация -> готово/нужна проверка
не публиковать без review, если confidence низкий
не включать цену, наличие, склад или сроки поставки из внешних источников
```

### 19.4 Запрещено

```text
придумывать преимущества
добавлять автомобили, которых нет в источнике
обещать наличие или быструю доставку
использовать цену источника
подменять факты маркетинговым текстом
```

### 19.5 Контекст для AI-агента

AI-агент должен получать не только сырые поля `Product`, но и enrichment context:

```text
Product.name
Product.brand
Product.article
Product.category_1c
Product.condition
Product.description_1c
ProductAttribute[]
ProductCrossCode[]
VehicleFitment[]
ProductEnrichmentFact[]
последний ProductParseJob.status
последний ProductParseJob.source_url
```

Правило по коммерческим данным:

```text
цена и остаток из нашей БД могут использоваться только если текущий бизнес-сценарий описания этого требует
цена/наличие/склад из внешнего источника не используются никогда
```

Рекомендация для качества:

```text
если применяемость подтверждена parser-ом:
  описание может уверенно писать "подходит для ..."

если применяемость отсутствует или needs_review:
  описание должно писать осторожно: "проверьте совместимость по артикулу/OEM"
```

Для tenant-ов с `catalog_domain != auto_parts` существующая кнопка генерации не
должна запускать автозапчастный parser. В этом случае запускается обычный
AI-сценарий по базовым данным товара.

### 19.6 UX для существующей кнопки

Кнопку в интерфейсе не нужно переименовывать на MVP. Поведение меняется внутри:

```text

  -> при необходимости запустить enrichment
  -> запустить AI generation
  -> обновить title_ai/description_ai
```

Если enrichment занимает время, UI должен показывать понятный статус:

```text

```

## 25. Критерии готовности MVP

MVP считается готовым, если:

- Можно отправить `brand + article` через API.
- Создается `ProductParseJob`.
- Celery-задача парсит `tachka`.
- Находится и обогащается существующий `Product` или создается новый только в согласованном сценарии.
- Сохраняются характеристики.
- Сохраняются OEM/cross-коды.
- Сохраняется применяемость.
- Сохраняются URL/кандидаты изображений или изображения передаются в существующий pipeline.
- Сохраняются факты, пригодные для полезного описания.
- `Product.price`, `Product.stock_qty`, `Product.warehouse` не изменяются.
- В админке можно увидеть job и связанные данные товара.
- Ошибки не теряются, а сохраняются в job.
- Есть тесты на нормализацию и сохранение результата.
- Tenant isolation покрыт тестами.
- Tenant с `catalog_domain` вне `auto_parts/mixed` не может случайно запустить
  автозапчастный enrichment, но может запускать обычную AI-генерацию.
- Tenant с `catalog_domain=mixed` запускает parser только для товаров, у которых
  `ProductCatalogClassification.domain=auto_parts`.
- Есть массовое действие для предварительной классификации домена товара без
  внешних запросов.
- Базовый `PartCategory` существует как platform-level taxonomy слой без
  перезаписи tenant-категорий.

## 27. Роадмап enrichment/domain/category

### Уже реализовано

- Tenant-scoped enrichment моделей `ProductAttribute`, `ProductCrossCode`, `VehicleFitment`, `ProductEnrichmentFact`, `ProductParseJob`.
- Parser MVP для `tachka`.
- Запуск enrichment через Celery, включая `parse -> generate description`.
- Dashboard-блок enrichment и единая кнопка “Обогатить и сгенерировать”.
- Platform knowledge graph: `GlobalPart`, `GlobalPartRelation`, `GlobalPartFitment`.
- Source quality policy и auto-apply guardrails.
- Vehicle справочник v1: `VehicleMake`, `VehicleModel`.
- Tenant capability `catalog_domain`.
- Смешанный каталог `catalog_domain=mixed`.
- `ProductCatalogClassification` с `domain/confidence/source/reason/needs_review`.
- Bulk action `classify_catalog_domain` без внешних запросов.
- Базовая platform taxonomy `PartCategory`.

### Текущая стадия

Мы находимся между MVP enrichment и расширением источников. Главная задача этого
этапа — не добавить больше parser-ов любой ценой, а стабилизировать предметные
границы:

```text
какой tenant может использовать auto-parts enrichment
какой Product является автозапчастью
какие категории редактирует tenant
какие домены контролирует платформа
```

### P0. Tenant-категории и domain mapping

Цель: дать tenant-у практичное управление категориями без нарушения platform
guardrails.

Реализовано в MVP:

- `TenantCatalogCategory` как tenant-scoped справочник категорий.
- API/dashboard для создания категорий tenant-а.
- Связь категории с platform domain.
- Маппинг `Product.category_1c -> TenantCatalogCategory`.
- Использование tenant category как сигнала для `ProductCatalogClassification`.
- Фильтр товаров по tenant category на странице каталога.
- Массовое назначение tenant category выбранным товарам без изменения `category_1c`.
- Редактирование/deactivate tenant-категорий и удаление mappings в dashboard.

Осталось:

- Иерархическое дерево категорий, если понадобится после MVP.

Что нельзя делать:

- Нельзя заменять `CatalogDomain` tenant-категориями.
- Нельзя давать tenant-у создавать новые platform domains.
- Нельзя запускать auto-parts parser только потому, что tenant назвал категорию “Авто”.
- Нельзя перетирать `Product.category_1c` из 1С.

### P0. Merge-policy классификации

Перед ручным редактированием классификации нужно определить:

- rules-based классификация может обновлять только `source=rules`;
- `source=manual` не перетирается без `force`;
- `force=True` используется только для явного override, а не для фоновых bulk actions;
- низкая уверенность всегда `needs_review`;
- изменение tenant category может поставить classification на повторный расчет.

### P1. Приоритеты нескольких источников

После стабилизации категорий:

- добавить второй enrichment source;
- описать source priority/trust/capabilities;
- запретить auto-apply конфликтующих данных;
- сохранять source conflict как `needs_review`.

### P1. Operator review workflow

- Очередь товаров/fitments/classifications, требующих проверки.
- Approve/reject для применяемости и классификации.
- История решений оператора.

### P2. Расширение taxonomy

- `VehicleGeneration`, `VehicleModification`.
- Связь `PartCategory -> fitment_required`.
- Связь `TenantCatalogCategory -> PartCategory` для auto-parts tenant-ов.
