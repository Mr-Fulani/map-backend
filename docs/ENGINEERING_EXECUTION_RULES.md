# Правила выполнения больших изменений

Эти правила обязательны для людей и автоматизированных исполнителей. Их цель —
не допустить повторения ситуации, когда проверка текущего этапа превращается в
разработку нескольких будущих подсистем.

## 1. Один активный результат

Перед началом работы фиксируются:

- один пользовательский результат;
- список файлов или подсистем в границах задачи;
- проверка, после которой задача считается выполненной;
- явный список того, что сейчас не делается.

Новая идея не расширяет активную задачу автоматически.

## 2. Стадии нельзя перескакивать

Допустимый порядок:

1. код текущего этапа;
2. узкие тесты;
3. полный тест проекта;
4. проверка миграций на чистой и обновляемой базе;
5. тестовый deploy;
6. наблюдение;
7. только затем следующий этап.

Пока предыдущая стадия не прошла, код следующей стадии не пишется.

## 3. Как обрабатывать найденные риски

Каждая новая проблема относится к одной из категорий:

- **блокирует текущий работающий режим** — исправляется сейчас;
- **блокирует проверяемый пакет** — исправляется внутри этого пакета;
- **понадобится только при будущем включении** — записывается в backlog без
  реализации;
- **улучшение без текущей ошибки** — не входит в задачу.

Фраза «это пригодится потом» означает backlog, а не разрешение писать код.

## 4. Ограничение размера

Работа останавливается и заново делится, если достигнут любой порог:

- больше 20 production-файлов;
- больше 1 500 новых строк без тестов;
- больше двух последовательных миграций;
- новая очередь, новый режим настроек или новая внешняя интеграция;
- изменение более двух независимых подсистем.

Продолжение после порога требует нового согласованного плана.

## 5. Статусы без самообмана

Используются только следующие состояния:

- `NOT_STARTED` — работа не начата;
- `IN_PROGRESS` — есть незавершённые изменения;
- `CODE_READY` — код написан, но полный gate не пройден;
- `VERIFIED` — указанные проверки реально выполнены;
- `DEPLOYED_OFF` — код выложен, функция выключена;
- `ENABLED` — функция включена и наблюдается.

Нельзя ставить `[x]`, если рядом нет даты, команды проверки и результата.
`CODE_READY` не означает `VERIFIED`, а `DEPLOYED_OFF` не означает `ENABLED`.

## 6. Правила работы с подзадачами

- Подзадача получает только часть текущего согласованного этапа.
- Подзадача не начинает исправлять проблемы будущих этапов.
- Ревьюер сообщает будущий риск в backlog и не расширяет работу сам.
- После каждого нового критичного замечания сначала пересматривается план, а
  не создаётся новая цепочка реализации.
- Одновременно редактируемые файлы не выдаются нескольким исполнителям.

## 7. Обязательная контрольная точка

После каждого пакета публикуется короткий отчёт:

- что изменено простыми словами;
- какие файлы и миграции затронуты;
- какие команды тестов выполнены;
- что не проверено;
- можно ли выкладывать;
- какой следующий шаг и почему он нужен.

Без такого отчёта следующий пакет не начинается.

## 8. Единственный источник правды в документации

- `README.md` — что умеет продукт и какой режим сейчас рабочий;
- `AVITO_FEED_STATUS.md` — только текущее состояние;
- `AVITO_FEED_ROADMAP.md` — только порядок будущих пакетов;
- `DEPLOYMENT.md` — только команды выкладки и восстановления;
- `PRODUCTION_SECURITY.md` — только обязательные запреты и допущения;
- `RELEASE_CHECKLIST.md` — только проверяемые пункты конкретного релиза.

Описание реализации не копируется во все файлы. Остальные документы должны
ссылаться на главный источник.

## 9. Stop-the-line

Любой участник обязан остановить работу, если:

- текущий план больше не соответствует фактическим изменениям;
- полный тест не запускался после нескольких волн правок;
- рабочая копия содержит несвязанные изменения;
- будущая функция начала диктовать архитектуру текущего релиза;
- непонятно, что именно будет выложено.

После остановки разрешены только аудит, разделение, тестирование и исправление
подтверждённых ошибок.
